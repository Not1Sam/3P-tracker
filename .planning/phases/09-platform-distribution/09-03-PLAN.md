  <action>
1. Add a caching layer to `src/services/leaderboard-service.ts` for offline leaderboard data (per D-11). Use MMKV (already installed as `react-native-mmkv`) to store cached leaderboard entries. Create a helper module or inline cache functions within leaderboard-service.ts.

2. Cache structure: Store entries as JSON in MMKV under keys like `'leaderboard_friends_poop'`, `'leaderboard_friends_piss'`, `'leaderboard_global_poop'`, `'leaderboard_global_piss'`. Each cached value includes `{ entries: LeaderboardEntry[], cachedAt: number }` where `cachedAt` is `Date.now()`.

3. Modify `getFriendsLeaderboard` and `getGlobalLeaderboard` to use cache-first strategy (per D-11):
   - First, try to fetch from Supabase (existing logic).
   - If fetch succeeds: update MMKV cache with fresh data, return result.
   - If fetch fails (network error, Supabase error): read from MMKV cache, return cached entries. If no cache exists, return empty array.
   - Do NOT block on network state — always attempt fetch, fall back to cache on failure. This is simpler and more robust than checking `isConnected` first.

4. Add a `syncLeaderboards()` function that can be called on app open and periodically (per D-12). This function:
   - Checks if network is available (import and call `NetInfo.fetch()` directly — do NOT import the React hook in a non-React context).
   - If online: fetch both friends and global leaderboards for both types, update MMKV cache.
   - If offline: skip silently.
   - Returns `{ synced: boolean, timestamp: number }`.

5. Conflict resolution: Server wins (per D-13). The caching layer never pushes local changes to Supabase — it only reads. Local leaderboard data is always replaced by server data when available. This means the cache is read-only and there are no merge conflicts.

6. Add a `getLastCacheTime(type: LogType, board: 'friends' | 'global'): number | null` helper that returns the timestamp of the last successful cache update, or null if never cached. This can be used by UI to show "Last updated: X minutes ago" when displaying stale data.

7. Verify: leaderboard-service.ts compiles. Cache functions store/retrieve from MMKV. Cache-first strategy works: successful fetch updates cache, failed fetch returns cache. syncLeaderboards checks network before fetching.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → Supabase API | Network requests for leaderboard data — could fail or return stale data |
| Client → MMKV storage | Local cache — device-local, no external trust boundary |
| Client → NetInfo API | Network state detection — may not reflect actual internet reachability |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-06 | Tampering | MMKV cached leaderboard data | low | accept | Cache is read-only, replaced by server data on sync — tampering has no lasting impact |
| T-09-07 | Denial of Service | Network state detection | low | accept | NetInfo may give false positives (connected but no internet) — handled by try/catch on fetch |
| T-09-08 | Information Disclosure | Cached leaderboard entries in MMKV | low | accept | Contains only public leaderboard data (usernames, scores) — no private data cached |
</threat_model>
